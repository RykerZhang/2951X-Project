# skill-chains：技能链在哪里断？

CSCI 2951X 期末项目。这份文档写给组里每一个人：先讲清楚我们在研究什么，再讲代码怎么组织、谁做什么、怎么算做好。

> 一句话：我们搭一个小游戏世界，让几个写好的技能按固定顺序接力完成任务，看接力在哪一棒交接时掉了棒、为什么掉、agent 自己能不能看出来、怎么修。

---

## 1. 我们在研究什么

### 1.1 一个例子

任务是"做一把镐"，技能按顺序接力：

```
砍树 → 做木板 → 去基地 → 做镐
```

每个技能单独测试都没问题：
- `go_base` 的任务是"走进基地"，一进基地就停下，任务完成了
- `make_pickaxe` 只要有 2 块木板、站在工作台旁边，每次都能做成

但接起来就可能断：agent 一进基地就停了，工作台却在基地的另一头，做镐开始不了。

**两个技能各自都没错，交接的地方断了。** 这就是我们要研究的东西。

### 1.2 研究问题

1. 技能链断的时候，断在哪一类交接处（L1–L4）？哪个交接最弱？
2. 不同的"不完美来源"（世界的随机性、学错的规则）分别造成哪一类断点？
3. agent 只看自己能观察到的现象，能不能分清是哪一类断点？
4. 每类断点该怎么修？修完提升了多少？

第 3、4 条是老师在 proposal 批注里点名要的（"handbook"）。

### 1.3 我们不研究什么

- **不研究怎么选技能**：技能的顺序是写死的，控制器不做任何决定
- **不用 LLM，也不用规划器**：这是老师的意见
- **不研究怎么学技能本身**：技能的动作脚本是我们写好的

## 2. 核心概念

### 2.1 系统由四部分组成

```
  世界（地图、物品、配方、随机性）              env/world.py
        ↑ 技能只能调用世界的三个基本动作：走、采集、合成
  技能（每个只管自己的子目标）                  skills/library.py
        ↑ 按写死的顺序一个接一个调用
  控制器（不做决定，只按顺序执行）              experiments/run.py
        ↑ 每次调用前后都要问：能开始吗？做完了吗？
  规则（真实的，或者学出来的）                  learning/models.py
```

**世界**：10×5 的格子地图，分成森林、基地、矿区三个区域。有树、工作台、石头，以及木头、木板、镐、石头、熔炉这几种物品。

**技能**：一个技能就是一个 option，由三部分组成：

| 部分 | 符号 | 意思 | 代码 |
|---|---|---|---|
| 启动条件 | I | 什么状态下可以开始 | `initiation(f)` |
| 动作脚本 | π | 每一步做什么，写死的 | `policy(s, t)` |
| 终止条件 | T | 子目标达成了没有 | `subgoal(s)` |

**控制器**：手里只有一张写死的顺序表，一个接一个地调用技能。它不思考，所以不会帮忙补上技能之间的缝，缝在哪里，链就断在哪里。

**规则**：控制器每次都要问两个问题，由"规则"来回答：

| 时机 | 问题 | 函数 |
|---|---|---|
| 技能开始前 | 现在能开始这个技能吗？ | `can_start(skill, s)` |
| 技能执行的每一步 | 这个技能做完了吗？ | `is_done(skill, s)` |

控制器完全相信规则的回答。

### 2.2 真实规则 vs 学到的规则

| | 真实规则（`TrueModel`） | 学到的规则（`TreeModel`） |
|---|---|---|
| 从哪来 | 我们写技能时定下的 | 决策树从数据里学出来的 |
| 会不会错 | 永远不会 | 会，数据越少越容易错 |
| 现实中的 agent 有没有 | 没有，没人告诉它答案 | 有，这是它唯一能用的 |
| 在项目里干什么 | 给失败贴准确的标签；作为对照组和修法的上限 | 正式实验里控制器靠它做判断 |

例子（做镐）：
- 真实规则：`木板 ≥ 2` **并且** `在工作台旁`
- 数据少时可能学成：`木板 ≥ 2`，漏掉了"在工作台旁"

proposal 里的写法是"the initiation set and the termination condition are learned from data"。论文里叫它 learned initiation and termination classifiers，不要叫 model，免得和别的"模型"混淆。

### 2.3 规则是怎么学的

用机器学习里最简单的一种：监督学习的决策树（sklearn），几秒钟就能训练完。

1. **造数据**：随机生成一个状态，让技能真跑一次，记下"特征 + 成功/失败"。重复几百上千次
2. **训练**：每个技能训练两棵决策树，一棵学 I'（能不能开始），一棵学 T'（做完没有）
3. **使用**：控制器问 `can_start` / `is_done` 时，由决策树回答

注意：训练用的"成功/失败"必须是真跑出来的，**不能直接调用技能里写好的真实规则来填**，否则等于抄了答案。

特征 f(s) 定义在 `env/world.py` 的 `features()` 里：木头、木板、石头、镐、熔炉的数量，镐的耐久，所在区域，是否在工作台旁。

选决策树是因为它学出来的规则能直接打印出来读，一眼就能看出学错在哪。

### 2.4 符号表

为了方便打字，统一用下面这套。带撇号 ' 的都是学出来的。

| 符号 | 意思 |
|---|---|
| s | 完整的世界状态 |
| f(s) | 状态的抽象特征（决策树和启动条件只能看这个） |
| D_o | 技能 o 的动作**真正能成功**的状态集合 |
| I_o | 我们为技能 o 写的启动条件，只能用 f(s) 写 |
| I'_o | 学到的启动条件 |
| T_o | 真实的终止条件：子目标达成 |
| T'_o | 学到的终止条件 |

写论文时可以换回 options 框架的标准写法（β 表示终止条件）。

## 3. 四类断点

### 3.1 断点在链条上的位置

```
上一个技能结束 ─L4/L1─▶ A 启动 ─L2─▶ A 执行 ─L3─▶ A 结束 ─L4/L1─▶ B 启动 ...
```

方框是每一步自己做的事（单独看都是对的），箭头是交接，失败都发生在箭头上。

| 断点 | 一句话 | 例子 |
|---|---|---|
| **L1** 判断错了 | 状态其实能开始，学到的 I' 却说不能，链条白白卡住 | I' 学成了"要 3 块木板才能做镐" |
| **L2** 启动条件不完整 | 状态满足 I，但动作还依赖了 I 没写的东西，执行到一半失败 | 挖石头的路线是写死的，石头换了位置就走不到 |
| **L3** 停的时机不对 | 学到的 T' 让技能停早或停晚 | 停早：做木板只做了 1 块就停；停晚：多挖石头把镐用坏了 |
| **L4** 交接不匹配 | 上一个技能正确结束，但结束的状态不在下一个技能的 I 里 | 进了基地就停，没站在工作台旁边 |

L4 还要记一个子标签：
- **已察觉**：I' 也说"不能开始"，链条卡住
- **未察觉**：I' 误判"能开始"，技能一启动就失败

L1 和 L4 发生在同一个交接处，区别是：L4 是交过来的状态本身不对，L1 是状态没问题、接收的一方看错了。

### 3.2 为什么会有 L2

I 只能用少数几个抽象特征来写，而动作依赖的是完整的世界状态。比如挖石头的 I 是"有镐，并且在矿区"，但动作脚本还隐含了"石头在某个固定位置"。要把所有细节都写进 I，它就不再是抽象了。L2 测量的是：抽象丢掉的信息，有多少在执行中途变成了失败。

形式化地说：存在状态 s，使得 f(s) 满足 I_o，但 s 不在 D_o 里。

### 3.3 判定顺序（每次失败只有一个标签）

对链条里的每个技能，按时间顺序检查，**第一个不通过的检查就是这次失败的标签**：

1. **启动时**，看上一个技能留下的状态：
   - 状态不在 I_o 里 → **L4**（同时记录 I'_o 有没有察觉）
   - 状态在 I_o 里，但 I'_o 说不能开始 → **L1**
2. **执行中**：技能启动了，但没达成子目标就失败了 → **L2**（状态在 I_o 里，但不在 D_o 里）
3. **结束时**：
   - T'_o 说做完了，但 T_o 其实没达成 → **L3 停早**
   - T_o 早已达成，T'_o 却没让技能停下，而如果当时停下，下一个技能本来可以开始 → **L3 停晚**

都通过就进入下一个技能。都不属于的标为 **other**。

代码在 `diagnostics/label.py` 的 `label()` 里。

> 待组会确认：proposal 里 L1 原本分乐观和悲观两种。现在把"乐观误判"（状态其实不能开始，I' 却说能）归到 L4 下面，作为"未察觉"；L1 只指悲观误判。

## 4. 失败从哪里来

### 4.1 三条缝

我们不会去规定"这一次在这里失败"。失败来自三条自然存在的缝：

| 来源 | 为什么会失败 | 主要造成 |
|---|---|---|
| 技能只管自己的子目标 | 不知道下一个技能需要什么 | L4、L3 停晚 |
| 世界有随机性 | 树、工作台、石头的位置会变，写死的动作可能走不通 | L2、L4 |
| 学到的规则有误差 | 训练数据有限 | L1、L3 停早、L4 未察觉 |

### 4.2 这不是 bug

- **bug**：技能从它自己能开始的状态出发，却完不成自己的子目标。这由单元测试检查，必须修
- **缝**：技能单独都对，接在一起有时接不上。这是我们要研究的

能不能把技能写到永远不失败？能，比如让 `go_base` 直接走到工作台旁边。但那等于写技能时就知道下一步是做镐。同一个技能会被很多条链复用，写的人不知道后面接什么，所以只能保证自己的子目标。

### 4.3 验证条件

**用真实规则、没有随机性时，所有链都应该 100% 成功。** 如果这时还出现失败，说明代码有 bug，必须先修好，后面的结果才可信。

## 5. 实验和最终结果

### 5.1 四种实验条件

| | 无随机性 | 有随机性 |
|---|---|---|
| **真实规则** | 验证条件，应该 100% 成功 | 只有随机性带来的失败 |
| **学到的规则** | 只有学习误差带来的失败 | 两种都有 |

每种条件跑 10 个随机种子，报告均值 ± 标准差。

### 5.2 论文里的图表

| # | 图表 | 回答什么 | 优先级 |
|---|---|---|---|
| R0 | 验证结果 | 零件都是好的，失败不是 bug | 必须 |
| R1 | 衔接矩阵热力图（每个格子是"A 结束后 B 能成功启动的概率"），分随机起点和链条起点两版 | 哪个交接最弱？单独测试能不能代表链条里的表现？ | 必须 |
| R2 | 矩阵预测的成功率 vs 整条链实际的成功率 | 两两交接能不能解释整条链的失败？ | 有时间再做 |
| R3 | 失败分布堆叠柱状图（4 种条件 × 每条链） | 哪种不完美来源造成哪类断点？ | 必须 |
| R4 | 旋钮曲线（数据量、偏乐观/偏悲观、随机性大小） | 失败怎么在各类断点之间转移？ | 有时间再做 |
| R5 | 混淆矩阵：真实标签 vs agent 凭现象猜的标签 | agent 能不能分清是哪类断点？ | 必须（老师要的） |
| R6 | Handbook：每类断点的现象、能否认出、修法、修前修后的成功率、oracle 上限 | 断了怎么修？修完提升多少？ | 必须（老师要的） |

### 5.3 Handbook 里的 oracle

oracle 的意思是"模拟器作弊，把某一环修到完美"。它现在的用途是**给修法定一个上限**，不再用来找瓶颈（那是衔接矩阵的工作）。

| 断点 | 实际修法（agent 真能做到） | oracle 修法（上限） |
|---|---|---|
| L1 | 多给数据，或把阈值调宽松 | 换成真实的 I |
| L3 | 用"子目标是否真的达成"重新训练 T' | 换成真实的 T |
| L4 | 在两个技能之间补一个过渡技能 | 模拟器直接把 agent 送到下一个技能能开始的位置 |
| L2 | 先找目标再走，不走固定路线 | 模拟器给出正确路线 |

至少要做 L4 的两种修法。L2 可以只写进 handbook，不实现。

### 5.4 写结论时注意

世界是我们自己设计的，所以"各类断点各占百分之多少"会随设计变化。

- ✅ "**在我们构建的世界和技能中**，做熔炉这条链 37% 的失败发生在 L4"
- ❌ "技能组合的失败中，37% 发生在 L4"

更有分量的是换了条件也不变的规律，比如"数据量增加，L1 和 L3 下降，L4 基本不变"，以及同一个世界里修前修后的对比。为了让结论更站得住：
- 在多个种子、多种布局下都跑，报告范围
- 旋钮在看结果之前定好，试运行只调整体成功率，不看各类断点的比例去调

## 6. 代码

### 6.1 运行

```bash
cd skill-chains                                        # 先进入项目根目录，下面的命令都在这里运行
pip install pytest scikit-learn                        # 现在的代码只依赖标准库 + pytest；决策树要 sklearn
python -m pytest -q                                    # 跑全部测试，现在应该是 13 passed
python -m experiments.run --model true   --noise 0     # 验证条件：应该全部 ok
python -m experiments.run --model true   --noise 0.5   # 加随机性
python -m experiments.run --model flawed --noise 0.5   # 加手写的"学错"规则
```

每次运行会在 `logs/` 下写一个 JSONL 日志，每次执行一个技能写一行。

### 6.2 目录和负责人

| 文件 | 内容 | 负责人 |
|---|---|---|
| `env/world.py` | 地图、状态、三个动作、随机性旋钮、特征 f(s) | 世界负责人 |
| `skills/library.py` | 技能和实验用的链 | 技能负责人 |
| `learning/models.py` | 真实规则 `TrueModel`、手写的 `HandFlawedModel`、决策树 `TreeModel`（TODO） | 学习线 |
| `diagnostics/label.py` | `label()` 上帝视角标签；`label_runtime()` agent 视角标签（TODO） | 归因线 |
| `experiments/run.py` | 执行循环、日志、批量实验 | 实验与分析线 |
| `analysis/plots.py` | 画图（TODO） | 实验与分析线 |
| `tests/` | 测试，每条线给自己的部分加 | 全员 |

项目里没有 `__init__.py`：Python 3.3 以后，普通文件夹也能直接当成包来导入。要注意三点：
- **`python -m experiments.run` 必须在 `skill-chains/` 根目录下运行**，否则会报 `No module named 'experiments'`。
- **根目录下的 `conftest.py` 不要删。** 它让 pytest 不管从哪个文件夹启动，都能找到 `env`、`skills` 这些模块。删掉以后，从上一级文件夹跑测试会报 `No module named 'env'`。
- 不同文件夹里的测试文件不要重名，否则 pytest 会报 "import file mismatch"。

### 6.3 共享合同（改之前先在群里说）

- **技能**：`subgoal(s)`、`initiation(f)`、`policy(s, t)` 三个函数；`initiation` 只能看 `features(s)`
- **规则**：`can_start(skill, s)`、`is_done(skill, s)`；学到的规则内部只能用 `features(s)`
- **世界**：`Env.reset()`、`Env.step(s, a) -> (新状态, 是否成功)`；所有随机只用 `env.rng`，保证同一个种子结果完全一样
- **日志**：每次执行一个技能写一行 JSON，字段见 `experiments/run.py`；`label_runtime` 字段已经留好位置
- **实验和分析分开**：实验只写日志，画图只读日志，画图时不重新跑实验

### 6.4 写技能的约定

- 导航技能 `go_xxx` 走到目标区域就停，不负责走到区域里的某个具体位置
- 合成技能原地合成，不自己走动
- 采集技能在当前区域里找资源
- **不要为了制造或避免某类断点去改技能**，断点要自己显现

### 6.5 骨架现在跑出来的结果（10 个种子 × 每条链 50 次）

| 条件 | 做熔炉这条链 |
|---|---|
| 真实规则，无随机性 | ok 100%（验证条件通过） |
| 真实规则，随机性 0.5 | ok 31%，L2 32%，L4 已察觉 37% |
| 手写学错规则，随机性 0.5 | ok 17%，L1 5%，L2 22%，L3 停早 30%，L4 已察觉 18%，L4 未察觉 9% |

**这些数字只用来检查骨架是否正常，不是实验结论。** L1 和 L3 来自手写的错误，正式实验必须换成决策树。
